# 부품 확인 → 새 회로·코드 (2026-10-27)

기본 목적을 원본 배선 복원에서 **관측 부품을 활용한 새 설계**로 변경했다. 원본 프로젝트는 보존하며 부품 목록과 새 설계의 근거를 별도 기록한다.

## 사용 순서

1. 사진 또는 영상을 업로드한다. 영상은 기존 추출기의 최대 6개 프레임을 함께 전달한다.
2. Sol이 부품 종류·모델 후보·표식·수량·관측 영역·확인할 사항을 구조화한 목록으로 반환한다. 기존 배선·가림 가설·핀 연결은 이 호출에 전달하지 않는다. 부품 후보는 INFERRED 또는 UNKNOWN이며 자동 CONFIRMED 처리는 없다.
3. 화면에서 각 부품의 실제 모델·정격·핀 라벨을 자료와 대조한다. 관측 부품을 설계 역할에 배정하거나 추가 준비 부품으로 지정한다. 핵심 개발보드와 LCD는 입력에서 관측된 부품이어야 한다.
4. 새 설계를 선택하고 확인 근거를 작성한다. 추가 부품이 있으면 규격·수량 준비 여부를 확인한다. 새 프로젝트와 새 코드를 만든다.
5. KiCad MCP 실행 버튼으로 새 회로도 → netlist 연결 대조 → ERC를 실행한다. 결과 화면에서 회로도·검사 기록·Arduino 코드를 다운로드한다. 조립 가이드는 새 Graph의 물리 핀 라벨을 사용한다.

## 현재 지원하는 새 설계

- ESP32-DevKitC V4 + LED + 버튼 + 220Ω/10kΩ 저항: 버튼을 누르면 LED 켜기.
- Arduino UNO R3 + 5V HD44780 호환 16×2 병렬 LCD + 10kΩ 가변저항 + 백라이트용 220Ω 저항: 새 문구와 경과 시간 표시. I2C 백팩 LCD는 해당하지 않는다.

저항값은 **새 설계 목표값**이며 사진에서 읽은 값으로 둔갑시키지 않는다. 모델명/값/핀을 확인할 수 없으면 실물 검사 또는 부품 교체가 필요하다. 브레드보드·점퍼선은 조립 준비물이며 전기 부품 역할 배정과 구분한다. 목록의 나머지 부품은 자동으로 회로에 넣지 않는다. 다른 조합의 범용 자동 설계·임의 코드 생성은 아직 지원하지 않는다.

기본 부품 식별은 Sol 1회다. 검토된 두 설계는 정해진 설계 규칙으로 구성하므로 Astra를 추가 호출하지 않는다. 기존 고급 회로 추론 요청은 근거가 있는 어려운 구간에만 Astra를 최대 1회 호출하는 정책을 유지한다.

## 데이터와 모듈

- `backend/design/models.py`: 관측 부품 목록과 새 설계 요청 형식.
- `inventory.py`: 배선 정보 없는 모델 입력, 관측 영역 검사, 부품 분석 계획 저장.
- `recipes.py`: 두 지원 구성의 연결 사양과 LCD 코드-회로 일치 계약.
- `routes.py`: 원본 리비전/해시, 부품 종류·수량·추가 부품 확인 검사. 새 프로젝트 생성.
- `firmware.py`: 검증된 LCD 연결 사양으로 LiquidCrystal 코드 생성.
- `frontend/inventory.js`: 부품 영역/후보 표시, 사양 링크, 역할 배정, 새 설계 생성.

`designs/<new_project>/provenance.json`에 원본 프로젝트·분석 계획·사용 부품·추가 부품·확인 근거를 저장한다. 새 Graph의 CONFIRMED는 명시한 설계 사양을 뜻하며 실물 동작 검증은 아니다. 수정 후 코드 연결·부품값·물리 핀 매핑 계약에 어긋나면 코드 생성을 막는다.

UNO/LCD는 이름을 가진 **인터페이스용 심벌**이다. KiCad 심벌의 표시 포트 번호는 실제 보드/16핀 LCD의 물리 핀 번호가 아니다. 심벌 속성의 `Physical pin labels`와 웹 가이드를 사용한다. 해당 모듈 장착 풋프린트는 미지정이며 LCD의 PCB 자동 생성·SPICE는 차단한다.

설계 근거: [Arduino UNO R3 공식 pinout](https://docs.arduino.cc/resources/pinouts/A000066-full-pinout.pdf), [Arduino 공식 병렬 LCD 가이드](https://github.com/arduino/docs-content/blob/main/content/learn/04.electronics/03.lcd-displays/lcd-displays.md).

## 검증과 한계

- 전체 자동 테스트 **193개 통과**, 이후 부품 수량 초과 사례를 추가한 부품 우선 테스트 **15개 통과**. 원본 보존, 검토 누락·다른 종류·수량 초과·오래된 분석·코드 삽입 차단, 영상 프레임 전달, 핀/연결/값 변경 차단 포함.
- 실제 MCP LCD 생성: 연결 대조 PASS, ERC PASS. `outputs/parts-first-validation/e5b19582b8e64101b26f24b26dd0eea3/execution.json`.
- 별도 8767 테스트 서버에서 카메라 사진 업로드 API → 고정 부품 응답 → 브라우저 부품 배정 → 새 설계 → 실제 MCP 생성/PASS → SVG 표시를 확인했다. 모델 인식은 테스트용 고정 응답이며 실제 인식 결과가 아니다. 원본 운영 프로젝트는 변경하지 않았다.
- 브라우저 파일 선택 업로드는 이전에 확인한 확장 프로그램 로컬 파일 접근 제한 때문에 이번에는 HTTP API로 입력했다. 브라우저 사양 검토·생성·실행은 실제 버튼으로 검증했다.
- 실 Sol/Astra 호출, 인식 정확도 평가, Arduino 컴파일·업로드·실물 작동은 이번 검증 범위 밖이다. 노출된 API 키를 사용하지 않았다.
- ERC는 회로 규칙 검사다. 커넥터 인터페이스 심벌의 정격, 모델 호환성, 실물 조립의 정확성까지 증명하지 않는다.

## 입력·출력 중심 화면

화면을 ① 사진·영상 입력 → ② 부품 확인 → ③ 새 회로 구성 → ④ 결과 확인 순서로 배치한다. 상단 고정 단계 안내와 각 단계의 이전·다음 버튼으로 이동한다. 부품 목록이 없거나 결과가 준비되지 않으면 해당 다음 버튼을 비활성화한다. 새 설계 프로젝트에서도 원본 사진을 유지하며 추가 부품을 구분한다. 출력 탭, 확대 보기, 다운로드는 ④ 결과 확인에 배치했다. ③에서 설계를 생성하면 ④로 자동 이동한다. 회로 구성은 사용자가 명시적으로 선택하며 초기 선택은 비워둔다. 기존 단계별 편집 도구와 근거·검증 내역은 기본으로 접힌 토글에 유지한다. 필수 확인 입력이 누락된 채 생성 버튼을 누르면 해당 토글을 자동으로 펼치며 생성 조건은 그대로 유지한다.

브라우저에서 입력 이미지 로딩, 기존 LCD 출력의 회로·코드·조립 탭, 확대/닫기, 근거 토글, 필수 확인 누락 시 생성 차단과 자동 펼침을 확인했다. 콘솔 오류·중복 HTML ID 없음. 모델 재호출·회로 재생성 없이 기존 테스트 산출물로 UI를 검증했다. 화면 기록: `outputs/parts-first-validation/io-layout-verified.png`.

단계 배치 검증: 실제 DOM 순서 1→2→3→4, 다음/이전 이동, 근거 기본 접힘, ② 목록과 ③ 구성 폼 분리 확인. 격리된 테스트 프로젝트에서 ③ 부품 배정·생성 후 새 프로젝트/코드 생성과 ④ 자동 이동을 확인했다. 모델 재호출 및 운영 프로젝트 수정 없음.

## 보드·부품 기반 자동 새 회로 구성 (2026-10-27)

사진 분석으로 얻은 Inventory를 `backend/design/proposals.py`가 받아 보드 계열,
부품 종류, 수량에 맞는 검토된 회로를 선택하고 부품을 자동 배정한다.
`GET /api/projects/{project}/inventory/{plan}/proposals`는 원본 Graph를 수정하지
않고 연결표, 설계 사양, 코드, 추가 부품, 잔여 부품을 반환한다. 모델 재호출은 없다.
프런트엔드 ③에서 추천 구성, 실제 선이 연결된 회로 미리보기, Arduino 코드를
확인할 수 있다. 실물 검토 이후 기존 생성 API로 별도 프로젝트를 만든다.

지원: UNO R3 저항 분압 읽기 / UNO 병렬 LCD / ESP32 LED·버튼.
이 구현은 제한된 회로 규칙을 선택·구성하며 임의 부품의 범용 AI 회로 합성은 아니다.
지원되지 않는 보드, 여러 보드 후보, UNKNOWN 부품, I2C LCD→병렬 LCD 오배정은
보류 또는 거부한다. 서버에서도 호환성과 수량을 검사한다.

현재 사진 `3fb56b7a96be491cb9059a090e564487`의 저장된 실제 모델 분석 결과:
UNO 계열 + 저항 5개 후보 → UNO와 저항 2개를 사용하는 분압 읽기 회로 추천.
나머지 저항 3개와 미식별 부품은 사용하지 않는다. 브레드보드·점퍼선은 조립 준비물.
R1=R2=10kΩ은 **새 설계값**이다. 사진에서 판독한 값이 아니므로 측정·교체가 필요하다.

새 회로: UNO 5V → R1 10k → A0 측정점 → R2 10k → GND.
USB 한 곳으로 공급하며 외부 전원을 측정하는 회로가 아니다.
`analogRead(A0)`와 115200 baud 시리얼 출력 코드를 생성한다.
약 512 / 0.5 / 2.5V는 이상적인 계산 예상이며 측정 결과가 아니다.
5V 전압 표시는 실제 AVcc를 측정하지 않은 추정치다.
핀은 [Arduino 공식 UNO R3 pinout](https://docs.arduino.cc/resources/pinouts/A000066-full-pinout.pdf)을 기준으로 정했다.

검증: 전체 pytest 210개 통과. 분리된 `outputs/parts-composition/mcp-51ebd6e88d8547eb87b6018366ef519a`에서
실제 KiCad MCP 생성, Graph-netlist 대조 PASS, ERC PASS.
이는 제안 사양의 회로 검증이며 사진 속 실물의 모델/저항값 검증이 아니다.
펌웨어 컴파일·업로드·실물 동작 시험·PCB 생성은 수행하지 않았다.
기존 사진 프로젝트와 기존 KiCad 프로젝트는 변경하지 않았다.

## 새 UNO 회로의 실제 ngspice 해석 (2026-10-27)

이미 설치된 libngspice 공유 라이브러리를 활용했다. 별도 설치나 클라우드 호출 없이
백엔드의 격리된 worker 프로세스에서 계산한다. 엔진이 없거나 결과가 잘못되면
실패를 반환하며 합성 파형으로 대체하지 않는다.

- ③ 자동 회로 제안 아래 `시뮬레이션 실행`: 실물 검토를 확정하지 않고 새 설계 사양만 시험.
- ④ 생성된 회로의 `시뮬레이션` 탭: 현재 Graph 버전의 계산 결과.
- 지원 분석: transient(시간 응답, 0→5V/1ms 시험 전원), dc(공급 전압 0~5V 스윕).
- Circuit Graph의 동일 net 이름/연결에서 SPICE 저항 연결을 생성한다.
- 결과: CH1=VCC_5V, CH2=TP_DIVIDER, 전류, 저항 전력, 수치 검증 PASS/FAIL.
- 분압 공식, 옴의 법칙, A0 범위, 5V 종료 조건을 독립적으로 검사한다.
- 입력 revision·Graph 해시·inventory plan으로 결과를 묶는다. 오래된 분석은 거부한다.
- 외부에서 임의 SPICE 명령을 받지 않는다. 지원 프로필과 분석 명령만 허용한다.

실제 계산: 5V, R1=R2=10kΩ에서 A0=2.5V, 전류=0.25mA,
저항별 전력=0.625mW. DC와 transient 모두 PASS.
`outputs/parts-composition/simulation/photo-transient` 및 `photo-dc`에
실제 웹 실행 결과와 SPICE 입력을 보관했다. 원본 사진 Graph는 변경하지 않았다.
전체 테스트 219개 통과; 브라우저에서 두 분석 실행과 결과 표시 확인.

검증 범위: 이상적 전원·저항·무부하 A0. 사진 속 저항값, 실제 부품 정격,
공차, 배선 기생성분, ADC 샘플링 부하, MCU 명령 실행은 검증하지 않았다.
ADC 512 예상은 전압 비율 계산이며 펌웨어 실행 결과가 아니다.
회로 계산 PASS와 실제 조립 성공을 구분한다. LCD 시뮬레이션은 미지원이다.
기존 RC 및 ESP32 근사 회로의 ngspice 지원은 유지한다.

선정 근거:
- https://ngspice.sourceforge.io/shared.html — netlist 입력, 계산 실행, 결과 벡터 조회를 지원하는 공유 라이브러리.
- https://ngspice.sourceforge.io/devel.html — 대체로 modified BSD 라이선스이며 일부 소스는 별도 라이선스.
- https://github.com/buserror/simavr — AVR 펌웨어·ADC·UART 실행 엔진. 후속 구현에서 프로젝트 내부 툴체인으로 연결했다. 현재 범위는 `embedded-simulator.md` 참조.
