# 사진·영상의 기능을 새 회로로 재구현

현재 분석 순서는 [구성품 우선 워크플로우](components-first.md)로 변경했다. 아래는 이전 구현 기록이다.

2026-10-27 구현. 물리적인 원본 배선·원래 소스 코드 복원과 구분한다.

## 동작 흐름

사진 / 추출 영상 프레임 → Sol 부품·기능 분석 → FunctionIntent → 기능에 맞는 검증된 회로 규칙 선택 → 부품·핀 호환성 확인 → 새 Circuit Graph와 코드 → 기존 KiCad MCP 계획·연결 대조·ERC.

FunctionIntent는 동작 종류, 관측 기반 추론/미확인/사용자 지정 상태, 입력 조건, 출력 반응, 이미지 ID별 관측 근거, 미확인 정보, 성공 조건, LCD 표시 문구를 저장한다. 부품이 있다고 그 기능이 동작한다고 간주하지 않는다. 영상은 기존 최대 6개 추출 프레임을 분석하므로 빠른 동작이나 타이밍을 놓칠 수 있다.

③ **재현할 기능**에서 입력·출력을 확인한다. 기능이 명확하면 일치하는 회로만 제안한다. 모르면 직접 동작을 지정하거나 새 기능 분석을 실행한다. 이전 parts-first 분석에는 동작 근거가 없으므로 자동으로 기능을 보충하지 않는다.

## 현재 지원

- UNO + 병렬 LCD: 지정한 16자 이내 ASCII 문구를 고정 표시. 기존 코드의 불필요한 경과 시간 출력 제거. 표시 문구가 없으면 확인 요청.
- UNO LED: 지속 점등 / 500ms 점멸 / 20ms마다 PWM 값을 5씩 증감. 목표 선택 → 회로·코드 생성 → Velxio 새 탭 → ▶ 실행. 세부 값은 새 설계 사양이다.
- UNO 분압: 보드 5V에 연결된 두 저항 사이를 A0로 읽고 200ms마다 시리얼 출력.
- ESP32 버튼·LED: 누르는 동안 켜지고 놓으면 꺼짐. 토글·점멸과 구분.

분압은 저항을 발견했다는 이유만으로 자동 추천하지 않는다. 기능 분류가 일치하고 호환 부품 조건도 맞아야 한다. 로봇·주차·모터 제어·임의 센서 동작·토글 등은 아직 추가 회로·코드 규칙이 필요하며, 기존 예제로 대체하지 않는다. 즉 임의의 영상에서 모든 기능을 설계하는 범용 에이전트가 완성된 것은 아니다.

## 변경 파일과 계약

- `backend/design/function.py`: 기능 데이터 모델·적합한 회로 필터·성공 조건.
- `backend/planner/provider.py`, `backend/design/inventory.py`: 구조화된 기능 분석 출력. 함수의 관측 이미지 ID를 검증하고 AI가 사용자 확인 상태를 만들어내지 못하게 한다.
- `backend/design/routes.py`: `/inventory/{pid}/function` 사용자 동작 지정 API, 기능 버전 해시와 확인 상태 검사. 원본 이미지·회로 데이터는 수정하지 않는다.
- `backend/design/firmware.py`, `backend/integration.py`: LCD 문구와 고정 표시 동작을 생성·재조회·다운로드에서 일관되게 유지.
- `frontend/function-intent.js`: 입력/출력 핵심 표시, 근거 토글, 기능 확인·변경.

기능을 변경하면 이전 function_version의 생성 요청을 409로 차단한다. 다른 기능의 회로를 강제 요청해도 생성하지 않는다. 결과 provenance에 기능 사양과 확인 기록을 저장하며 `functional_equivalence_verified=false`를 유지한다. 사용자 확인이나 코드 생성 자체는 실물 기능 동등성 검증이 아니다.

## 검증 결과

전체 테스트 240개 통과. 실제 외부 모델 호출 없이 구조화된 응답 fixtures로 동작 계약을 검증했다.

- 동작 미확인 시 분압 자동 선택 금지
- LCD의 Javalab.org 문구 보존, 추가 시간 카운터 없음
- 주차 로봇 기능을 지원 회로로 대체하지 않음
- 가짜 이미지 ID와 모델의 USER_DEFINED 상태 차단
- 기능 변경 후 이전 생성 요청 차단
- 생성·재조회·다운로드 코드의 동일 동작 유지
- 원본 프로젝트 불변

이번 검증은 새 프롬프트의 실제 사진·영상 인식 정확도 측정, LCD 펌웨어 실물 업로드, 임의 회로의 기능 동등성 증명을 포함하지 않는다.

## 기능 후보 추론 보완

확정 관측과 기능 후보를 분리한다. 이제 정지 사진에서 동작을 증명하지 못해도 가능한 기능 1~3개를 제시한다. 각 후보는 `INFERRED` 상태, 관측 부품·이미지 참조, 정성적 추정 강도, 가정, 예상 입력·출력, 후보를 구분할 확인 방법을 가진다. 추정 강도는 측정된 정확도·확률이 아니다.

새 멀티모달 응답에는 `function_hypotheses`가 포함된다. 기존 분석에는 저장된 부품 관측으로 후보를 만드는 규칙을 적용하며, 이를 새 모델 호출이나 새 이미지 분석으로 표시하지 않는다. 현재 LED 사진에서는 점등 제어(중간), 주기적 점멸(낮음), PWM 밝기 조절(낮음)을 제안한다. 켜진 한 순간으로 점멸 주기·GPIO 번호·보드 전압·저항값을 확정하지 않는다.

사용자가 후보를 고르면 `/function-candidate`가 그것을 **재현할 설계 목표**로 저장한다. 원래 동작이 확인됐다는 의미가 아니므로 가정과 근거는 보존한다. 아직 지원하지 않는 후보도 추론 목록에서 숨기지 않으며, 회로 생성 지원 여부는 별도로 표시한다.

추가 검증: 후보 생성·없는 부품/이미지 참조 거부·원본 보존·후보 선택 API 등 관련 테스트 26개 통과. 기존 저장된 관측으로 현재 사진의 후보를 생성했고, 새 모델 호출은 실행하지 않았다.
