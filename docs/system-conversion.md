# 편집기 시스템 전환

편집기 상단 **시스템 전환 → 대상 보드 → 회로·코드 전환 → 새 탭에서 열기**.

대상은 Arduino UNO, Pico RP2040, ESP32 DevKit V1, Raspberry Pi 4다. 원본 탭과 저장 자료를 보존하며 대상마다 별도 초안을 만든다. 전환 중 또는 결과 생성 후 원본이 바뀌면 오래된 결과를 적용하지 않는다.

## 처리 순서

1. 현재 편집한 부품·실제 배선·코드 파일을 읽는다. 과거 사진 분석의 코드를 재사용하지 않는다.
2. 빵판 내부 연결과 직렬 저항을 따라 GPIO의 입력·아날로그 입력·PWM·서보·일반 출력 역할을 구한다.
3. 보드 규칙으로 핀·전원·배선을 확정한다. 주변 부품, 값, 구조물, 장착 위치, 빵판 구멍과 기존 부품 간 배선을 유지한다.
4. **OpenAI Sol은 코드만 작성한다.** 현재 소스와 고정된 대상 회로·핀 대응·ADC 범위·전압 보정 정보를 전달한다. 사진·구조 좌표·파일 경로·과거 분석 전체는 전달하지 않는다.
5. 응답 형식, 대상 언어, 선언한 GPIO와 회로의 일치, 코드에서 발견되는 잘못된 GPIO를 검사한다. 대상 코드와 시험 항목만 적용한다.
6. 새 편집기에서 컴파일·실행·입출력 검사를 진행한다. 코드 작성 성공은 동작 검증 성공이 아니다.

`backend/translation/portable.py`가 회로 규칙과 공통 모델을 만든다. `backend/translation/system.py`가 코드 전용 `FirmwarePlan` 응답을 받는다. 부품·배선·핀 변경 항목을 AI가 반환하면 거부한다. AI에 전달하는 데이터도 복사하여 모델 어댑터가 서버의 확정 회로를 수정하지 못하게 한다. [OpenAI Docs의 엄격한 구조화 응답](https://developers.openai.com/api/docs/guides/structured-outputs)을 기존 Responses 경로에서 사용한다.

일반 경로는 `allow_ai: true`이며 UI 기본값이다. 알려진 버튼 LED 예제도 이 설정에서는 Sol이 코드를 작성한다. AI를 끄면 코드와 실제 연결이 일치하는 검토된 버튼 LED 기본 코드만 사용한다. 서버 키와 API 요금이 필요하며 자동 재시도는 하지 않는다.

## 회로 규칙과 한계

- LED, 버튼, 가변저항, 광센서, 토양 센서, 초음파 센서, 서보, 부저, MOSFET 제어와 병렬 LCD 신호의 역할을 지원한다. 나머지 전원·수동 부품은 기존 연결을 유지한다.
- 5V 센서 입력을 3.3V GPIO로 전환할 때 2.2kΩ·3.3kΩ 분압을 실제 부품과 배선으로 추가한다. 코드에는 비율을 전달하여 ADC 임계값을 보정한다. 이미 있는 지원 분압망은 다시 추가하지 않는다.
- ESP32 VIN을 5V 출력으로 가정하지 않는다. 기존 5V 주변장치가 있으면 외부 5V 전원을 추가한다.
- Pico PWM 출력은 서로 다른 PWM 슬라이스에 배정한다. 슬라이스는 주파수 설정을 공유하는 출력 묶음이다.
- Raspberry Pi 4에는 ADC가 없다. 아날로그 입력 전환은 지원 ADC 부품이 마련되기 전까지 모델 호출 전에 중단한다. 센서값을 가짜 값으로 대체하지 않는다.
- 단락, 미연결 부품, 알 수 없는 GPIO 역할, 지원하지 않는 저항망·특수 핀·버스, 핀 부족은 모델 호출 전에 알린다. 모든 임의 회로에 대한 범용 변환은 아니다.
- 입력은 보드 1개와 전자 부품 15개까지다. 전압 보완 후에도 보드 포함 16개 이내여야 한다. 구조물과 빵판은 제외한다.
- 코드의 GPIO 선언과 명시적 GPIO 호출은 검사하지만 임의 코드 전체의 의미와 타이밍을 증명하지 않는다. 실제 실행 검사와 사용자 검증이 필요하다.

공통 모델은 `embeddedVision.portable_system`에 역할, 원본·대상 핀, 보정 비율, 원본/대상 지문을 저장한다. 지문은 데이터 변경 여부를 확인하는 해시다. 다음 전환에서는 이 기록을 그대로 믿지 않고 현재 회로·코드를 다시 읽는다.

## API와 실행기

`POST /api/system-conversions/preview`, 본문 `{project, target, allow_ai}`. 기존 호출 호환을 위해 API의 생략된 `allow_ai` 기본값은 false다. UI는 true를 명시한다.

SaaS에서는 `/api/w/{workspace}/system-conversions/preview`를 사용하며 기존 작업자·권한·작업 한도·중복 방지를 유지한다. 결과 대기 중단은 이미 진행 중인 모델 작업 취소를 보장하지 않는다.

UNO는 avr8js+ngspice, Pico는 실제 MicroPython RP2040+ngspice를 사용한다. ESP32와 Linux Pi는 전용 실행 서비스가 필요하며 서비스 미연결을 실행 성공으로 표시하지 않는다. 구조물 간섭, 실제 전압 허용 오차와 실물 동등성은 별도 검증한다.

검증 자료는 `outputs/portable-system-conversion/`에 저장한다. 코드 모델 경로는 외부 전송 없는 테스트 대역으로 검사하며 실제 API 호출 검증과 구분한다.

최종 검사: 서버 128개·편집기 42개 통과. 현재 변환기로 생성한 버튼·밝기 조절·서보 회로는 실제 Pico MicroPython과 ngspice에서 입력/출력 검사를 통과했다. 이 3개 코드의 공급자는 테스트 대역이며 실제 AI 생성 품질을 검증한 결과는 아니다. Vite 빌드 성공, 기존 TypeScript 오류 359개 대비 추가 0개. 벤더 패치 32개 재적용 시 240개 파일 일치. 실행 서버 8897·8768·SaaS 8770의 전환·되돌리기·가이드 검사 통과. 재시작 전후 기존 입력·분석 파일 139개 동일. 실제 유료 모델 호출·브라우저 직접 조작·실물 검증은 진행하지 않았다.
