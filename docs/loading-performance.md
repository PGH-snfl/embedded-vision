# 편집기 로딩 개선

2026-11-04 로컬 Pi 2륜 사진 예제에서 관측한 병목은 서버가 아닌 브라우저의
동기 배치·배선 계산이었다. API 응답은 3~13 ms였으나 조립 계산이 끝나야
프로젝트를 가져오므로 주 화면이 계산 중 갱신되지 않았다.

- A* 경로 탐색에서 매번 후보 전체를 정렬하던 코드를 이진 힙 우선순위 큐로
  바꿨다. 낮은 비용 우선, 동일 비용은 최근 후보 우선인 기존 순서를 유지한다.
- 첫 조립과 사용자가 요청하는 최적화를 전용 Worker로 실행한다. Worker는
  화면과 분리된 계산 작업이다. 화면을 닫으면 취소하며 오류·45초 제한을 표시한다.
- 최적화 중 회로·구조·설계 버전이 바뀌면 오래된 계산 결과를 적용하지 않는다.
- 계산 결과의 첫 배선 경로를 전달하고 같은 구조·핀의 결과는 최대 두 개까지
  메모리에 재사용한다. 부품·단자 변화는 캐시를 무효화하며 선 색상만의 변화는
  다시 탐색하지 않는다.
- 최초 조립 직후에도 브라우저 초안을 저장한다. 기존 저장 배치는 재최적화하지
  않으므로 사용자 수정·삭제를 유지하고 다음 진입에서 계산을 생략한다.
- 운동 시뮬레이터 약 713 KB는 운동 미리보기를 실행할 때 불러온다.
- 로컬 편집기 서버는 gzip 압축과 해시가 있는 정적 파일의 장기 캐시를 사용한다.
  HTML은 재확인한다. SaaS의 인증 응답에 설정한 no-store는 변경하지 않는다.
- 프로그램 초기 다운로드, 회로 읽기, 배치 계산, 3D 준비 상태를 표시한다.
  iframe load 이벤트만으로 회로가 준비됐다고 표시하지 않는다.

## 측정

동일한 실제 프로젝트 데이터(관측 구조 8개 + 보완 11개 + 장착 부품 6개 +
논리 연결 8개)를 Node.js 22에서 실행했다. 계산과 경로 검사 기준 약
7.87초에서 1.83초로 감소했다. Vite가 빌드한 Worker를 별도 실행한 결과는
1.79초이며 주 스레드의 10 ms 타이머가 계산 중 177회 응답했다.
원래 코드·연결은 유지되며 미해결 경로 0개, 가상 배선 길이 1.11 m였다.

로컬 서버의 실제 index JS 응답은 4,733,052 B에서 gzip 1,342,874 B로
줄었다. 이는 계산·전송 측정이며 브라우저의 전체 로딩 시간을 측정한 값은
아니다. 이번 세션에서는 브라우저 제어 도구 오류로 화면·프레임 시간 검증을
완료하지 못했다.

회귀 검사: `assembly-loading.test.ts`, 기존 배치·배선·편집기·운동 브리지
검사, `test_workbench_delivery.py`, 프로젝트/운동 흐름 검사.
재설치: `velxio-whole-structure.patch` 다음 `velxio-loading.patch` 적용.
