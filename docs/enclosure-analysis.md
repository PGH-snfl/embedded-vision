# 외장 내부 구성 추론

2026-11-10 변경: 실제 사진 분석의 기본 경로를 `photo_system` 단일 호출로 통합했다. `PhotoSystemAnalysis` 응답의 `inventory`와 `design`에 구성품과 기능·내부 분석·부품 선정·배선·코드를 함께 받는다. 서버의 참조 검사와 데이터시트·편집기 생성은 유지한다. 구성품 목록은 전체 응답 도착 후 저장되며, 별도 1차 호출 결과를 먼저 보여주지는 않는다. 잘못된 응답에는 자동 추가 호출을 하지 않는다. `analysis_mode=single_call`, `model_call_count=1`과 단일 attempts 기록으로 호출 수를 표시한다. 기존 테스트/사용자 정의 단계형 provider는 호환되며, `single_call=False`로 이전 방식을 명시적으로 사용할 수 있다. 아래 두 호출 관련 기록은 이전 검증 이력이다.

외부 구성품과 구조를 분석한 뒤, 기능을 실행하기 위한 구체적인 부품·값·핀 연결·구조·코드를 선정한다. 선정 완료 상태는 `DESIGN_SELECTED`다. 사진 속 원본에 대한 관측 기록은 별도 비교 자료로 보존하고, 실제 내부 확인과 최종 판단은 사용자에게 있다.

## 분석 흐름

1. 기존 첫 번째 모델 호출이 보이는 구성품만 식별하고 목록을 저장한다.
2. 두 번째 기능 추론 호출이 `enclosure_analysis`와 `functional_build`를 함께 작성한다. 외장 → 전원부·제어부·구동부 → 개별 부품의 관계는 `parent_id`와 선정 부품의 `module_refs`로 연결한다.
3. 각 내부 후보에 목적·근거·모델 후보·대안·정성적 확신도를 저장한다. `status=INFERRED`, `photo_presence=UNKNOWN`만 허용한다.
4. 관측 부품 ID, 기능 후보 ID, 보완 부품 ID와 계층을 검사한다. 내부 후보를 원래 관측 목록에 합치지 않는다.
5. `functional_build`에서 부품마다 실제 실행 모델, 수량 1개 단위의 고유 ID, 선정값, 역할, 장착 외장과 위치를 결정한다. 전원·신호·접지를 연결하고 setup/loop가 있는 Arduino C++ 코드를 생성한다.
6. 지지대·장착판·브래킷·축이 필요하면 선정 치수로 추가하고, 외장은 부품과 배선 공간을 수용하도록 크기를 정한다. 이 치수는 새 설계값이다.
7. 초기 자유 설계 경로는 UNO와 `data/implementation-parts.json`의 17종 실행 모델을 사용한다. 실제 핀 이름과 허용 설정을 모델에 전달하고 부품·연결 참조를 검사한다. 외부 라이브러리 없이 Arduino 코어로 컴파일한다. 기존 다중 보드 경로는 유지한다.
8. 기존 분석도 급수·거리 표시·장애물 회피·기본 LED/LCD/센서 기능에 해당하면 추가 모델 호출 없이 기존 참조 회로로 구체화한다.
9. 부품 요약 JSON/HTML과 ③ 화면에 선정 부품·값·배선·코드를 먼저 제공한다. 사진의 보완 후보와 원본 확인 항목은 비교용 접힌 상세 정보에 둔다.

기존 두 번의 Sol 호출 구조를 사용하며, 이 기능만을 이유로 Astra를 자동 호출하지 않는다. 두 번째 응답의 출력 토큰 상한은 코드 생성을 포함해 18,000이다. 새 API 출력에는 nullable `enclosure_analysis`, `functional_build` 필드가 필수지만, 이전 저장 결과에 필드가 없어도 열 수 있다.

## 화면과 API

③의 **완성 설계·시뮬레이터 열기** 버튼은 `GET /api/projects/{project}/inventory/{plan}/functional-workbench?function_version=...`로 선정 회로를 연다. 가장 높은 기능 후보에 실행 설계가 있으면 기존 자동 시뮬레이터 이동에도 연결한다. 기존 `enclosure-study` API도 가능한 경우 선정 설계를 반환한다. 기존 분석의 새 모델 추론이 필요하면 사용자가 재분석을 시작하며, 서버가 자동 재과금하지 않는다.

새 `ai_functional_build` 프로젝트에는 실제 보드·부품·전기 핀·배선·펌웨어가 있다. 외장/선정 부품·배선/분해도를 전환하며, 외장을 닫으면 내부 부품과 관련 배선을 감춘다. 선정 부품을 클릭하면 역할·선정 사유·선정값을 표시한다. 기본 위치는 고정되며 이동 활성화를 켜야 이동한다. 보드의 선정 정보와 장착 위치도 VLX와 서버 저장에 보존한다.

전기 실행 기능을 구성할 수 없는 예전 분석에는 기존 `enclosure_hypothesis_view` 표시 모형이 남는다. 실행 회로를 만들 수 있는 기능을 이 표시 모형으로 대체하지 않는다. 사용자가 다른 기능을 선택하면 이전 기능의 실행 설계를 자동 적용하지 않는다.

- 내부 추론·기존 구성품 분석·시스템 추론·사진 구조·부품 우선 파이프라인: Python 검사 52개 통과.
- 자동 분석·자동 프로토타입·프로젝트 삭제: Python 검사 27개 통과.
- 내부 모형의 세 표시 방식, 전기 핀 배제, VLX 저장·복원, 선택 정보와 모드 변경: 신규 프런트엔드 검사 3개 통과. 관련 기존 구조물/급수/로딩/초기 동작 검사도 통과.
- 부품 트리의 HTML 이스케이프와 실패 시 빈 탭 종료: Node 검사 2개 통과.
- Vite 배포 빌드 성공. 전체 TypeScript 오류는 변경 전후 359개로 동일하며 새 오류는 없다. 전체 TypeScript 검사가 통과했다는 뜻은 아니다.
- 재설치용 23개 패치 적용 후 201개 파일이 현재 소스와 일치한다.
- 8897 API를 기존 데이터·환경을 유지해 재시작했고, 최신 분석 파일 및 8768 편집기 배포 파일의 HTTP 응답을 확인했다.

이번 기능 구현 보강에서는 새로운 다이얼 밝기 제어와 서보 제어 예제를 격리 컴파일러로 컴파일하고 실제 AVR 실행 모델로 실행했다. 다이얼 회로의 SPICE 전압에 따라 PWM 비율이 약 0/50/100%로 변하고, 서보 출력은 입력에 따라 1/2ms 펄스로 변하는 것을 검사했다. 선정 부품·배선·장착 위치 저장 및 복원 검사도 통과했다. 실제 사진에 대한 최신 결과는 `outputs/functional-build/live-result.json`에 별도로 기록한다. 브라우저 연결 오류 때문에 실제 GUI 조작/스크린샷 검증은 완료하지 못했다.

실제 등록된 급수 사진을 OpenAI API로 2회 분석했다. 응답은 기능 실행용 전자 부품 13개와 배선 22개, Arduino 코드를 작성했다. 최초에는 소비전력·공급전압·제어 임계값 같은 설계 사양을 런타임 설정으로 잘못 취급해 제외하는 문제가 있었다. 선정 사양은 부품표에 보존하고 지원되는 설정만 실행 모델에 적용하도록 수정한 뒤, 같은 응답을 추가 호출 없이 다시 처리했다. 생성된 코드가 컴파일됐고, 실제 AVR와 ngspice 실행에서 건조→펌프 ON, 젖음→OFF, 정지 버튼→OFF, 해제→ON을 검사했다. ON에서 펌프 전류 >0.24A, OFF에서 <0.001A였으며 해석한 펌프 출력으로 물 이동과 토양 피드백을 진행했다. 물통·화분·호스는 기존 동작 모형에 연결했다. 기존 사용자 프로젝트는 수정하지 않았다.

최종 관련 검사: Python 기능/내부/데이터시트 30개, 프런트엔드 기능/환경/저장 27개, 별도 DOM·데이터시트 검사 16개 통과. 앞서 기존 자동 분석·기능 선택·부품 단계·화면 이동을 포함한 Python 검사 68개도 통과했다. 범위가 겹치므로 이 숫자를 합산하지 않는다. Vite 빌드는 성공했고 TypeScript 기존 오류 359개에 새 오류는 추가되지 않았다.
